* What the ledger records

What does an eb-stack ledger say about a software tree, and why can a reader trust it years later?

** The problem

After years of rebuilds and rollbacks, someone asks what was installed at a path on a given day, from which module file, and who put it there.
A log that can be edited afterwards cannot answer that, nor can one that missed a publication because it was down that day, or holds one twice because a run retried.
And a record must not claim more than happened: that a build started is not that it finished, and software found on disk is not software seen being built.

** How eb-staged-rebuild handles it

*** The log and its signatures

The ledger belongs to eb-stack: =eb-stack ledger append= adds a record to a JSON Lines log and signs a new /head/, the size of the log and the root of a Merkle tree over its records, with an Ed25519 key.
=eb-stack ledger verify= proves that a record is in a signed head, and that a later head extends an earlier one, so a log rewritten after a head was signed no longer matches it.
eb-staged-rebuild signs and proves nothing itself: it runs those commands, with a time limit, and reads their first line.
It takes a record as delivered only when =append= exited 0, its receipt names the record's index, the head file it wrote has the size and root of the receipt, the log holds this record at that index, and, with a public key, =verify= proves it.

*** The records of a run

A run with =--ledger-config= adds two records for each module file it publishes:

- =started=, before the directories are exchanged;
- =finished=, after the run is =complete=.

Each names the module and the stable directory, =location=, which is the path the installation is used under; the generation and the hidden name are not the published place.
Each also carries the SHA-256 of the new module file and of the one it replaced, the run id, and an =event_id= made of the state root, the run, the module file and the stage.
A rollback adds a =correction= of each =finished= record, again as =started= and =finished=, with =corrects= set to the id of the record it corrects; a rollback of a run that recorded =started= and never =finished= adds an =aborted= record instead.
A run that =--force= published past the failed checks of =--verify= says so in its =started=, =finished= and =aborted= records, whose =build.verify= holds the result of the checks, =forced=, and the number of problems of each check; its corrections do not.
=retire= and =gc= add no records.

*** Once, and in order

The records go into the run's outbox, =runs/RUN_ID/outbox.json=, before they are delivered, and are delivered one at a time, in order.
A delivery without a receipt leaves the record pending, with the same bytes and the same =event_id=, and eb-stack answers a second append of a known =event_id= with =already recorded=, so a retry adds nothing.
With the ledger required, the default, a run does not exchange anything until its =started= records are acknowledged, and stops with exit status 75; =resume= delivers them and goes on.
A rollback waits for the =started= records of its correction in the same way, and =rollback= run again delivers them and goes on.
With ="required": false=, the run or the rollback goes on, and the records wait in the outbox for the next =resume= or =rollback=, whichever the message names.

*** Maintenance belongs to eb-stack

eb-staged-rebuild only appends the records of its own runs and rollbacks.
Reading and maintaining the log is eb-stack's: =eb-stack ledger backfill= records software installed before the ledger, =eb-stack ledger anchor= and =eb-stack ledger verify-anchors= keep and check one signed head per day, and =eb-stack ledger project= writes the history of each package.
A pipeline that records the outcome of other build commands appends those records itself with =eb-stack ledger append=.

** What was considered and turned down

- /Recording a publication after the exchange only./
  A crash between the exchange and the record would leave a published installation that the ledger never heard of; =started= comes first, so every publication has at least that record.
- /Signing and proving in eb-staged-rebuild./
  It would tie this program to the ledger's format; it depends only on eb-stack's command line and the first line that prints.
- /Recording the build command and its environment./
  They can hold credentials, so a record holds only the fields listed above.
- /Maintenance commands in eb-staged-rebuild./
  Backfill, anchors and the package history read and sign the ledger as a whole, not one run, so they live with the ledger in eb-stack.

** Limits

- The ledger records what eb-staged-rebuild did, not every change to the tree: a plain =eb=, a copy or a removal by hand leaves no record.
- Whoever holds the signing key can sign any log; daily anchors (=eb-stack ledger anchor=) protect the history only where the key's holder cannot change them.
