* How a rebuild is published

What happens between a complete generation and the moment users load the new installation, and how does a rollback undo it?

** The problem

A rebuild changes two things that users see: the directory =software/NAME/VERSION= and the module file that names it, and a build can install several modules at once.
Each change is a step that can fail, on a disk that is full, a permission that is missing, or a machine that stops.
A failure part way must not leave a module file that names a tree it does not belong to, nor a directory that no module file loads; and the published state has to stay undoable until the old tree is gone.

** How eb-staged-rebuild handles it

*** The order of the steps

After the build and its checks, the run goes through these steps under the state root's lock, and records each in its journal before it goes on:

1. A /preparation program/, if =--prepare= names one, gets the path of a JSON file that describes the publication, and may set permissions on the new tree and on the new module file; [[file:../howto/set-permissions.org][Set the permissions of a rebuild before it goes live]] has an example.
   It has to exit 0 and leave the tree complete.
2. With =--verify=, the checks of =verify=: that the libraries each program needs are found, that no file names the build directory or a temporary directory of EasyBuild, that Lmod loads the new module files, and that publishing would not change who may use the installation; [[file:../reference/verify.org][The checks before publication]] lists them.
   A generation that fails stays =built=, with nothing recorded in the ledger, unless =--force= publishes it all the same.
3. A =started= record for each module goes to the ledger, if =--ledger-config= names one; [[file:ledger.org][What the ledger records]] has the rest.
4. For each module, the live module file is copied to =runs/RUN_ID/backups/=, the paths the build wrote are changed to the stable path, and the new tree moves to its hidden name, =software/NAME/.VERSION.RUN_ID=.
5. For each module, the hidden tree and the live one are exchanged.
6. For each module, the new module file replaces the live one.
   It keeps the owner, the mode and the access-control list of the module file it replaces, unless the preparation program set others on the new one.
7. Links that EasyBuild made in the generation's module tree, such as the module files of a module class, are made in the live tree where nothing is at their path.
8. The run is =complete=, and the ledger gets a =finished= record for each module.

Every directory is exchanged before any module file is replaced, so a module file never names a tree of another run.
Steps 2 and 4 change nothing live.
When a step from 5 to 7 fails, the run exchanges back what it exchanged and puts back the module files it replaced; the journal says =built=, with =publish interrupted; old live tree restored=, and =resume= tries the publication again.

*** The exchange

The exchange is the =renameat2= call with =RENAME_EXCHANGE=, when the probe that the run recorded at its start says the filesystem supports it.
A filesystem that refuses the flag, with =EINVAL=, =ENOSYS= or =EOPNOTSUPP=, gets three ordinary renames instead: the live tree to a hold name, =software/NAME/.VERSION.RUN_ID.fallback-old=, the new tree to the live name, and the hold name to the hidden one.
Between the first two renames the stable path is missing.
A failure in the sequence puts the two names back before it is reported, and a run that was killed in it finds the hold name on =resume= and puts the names back then.
Any other error from the exchange leaves both names as they were.
The journal records which of the two each module got, as =swap_method=.
[[py:eb_staged_rebuild.swap.swap_directories]] and [[zig:eb-staged-rebuild.engine.run_mod.swap.swapDirectories]] do the exchange.

*** The module file

The new module file is written next to the live one, flushed to disk, and renamed over it, so a reader gets the old file or the new one.
Its owner and mode are set before its access-control list, because =chmod= can rewrite an NFSv4 list.
The lists it copies are the NFSv4 list of IBM Storage Scale, =system.gpfs_nfs4_acl=, the generic one, =system.nfs4_acl=, and the POSIX one, =system.posix_acl_access=; only the most native one present is written, and every one is read back to check it.

*** Rollback

=rollback= of a =complete= run does the same in reverse: it exchanges each hidden tree back into the stable path, last module first, puts back each module file from its backup, and removes the links the run made.
First it checks, by the completion marker, that each stable path holds the tree the run published, and refuses before it changes or records anything when one does not: after a later run of the same installation, that later run is rolled back first.
A failure part way exchanges back to the published state, and the rollback can run again.
The tree the run published stays under its hidden name until =gc= removes it.
With a ledger, the rollback adds a =correction= of each =finished= record.

*** Rolling back several runs

=rollback --latest= rolls back the newest =complete= run, by the time its publication completed.
=rollback --to GEN= rolls back every =complete= run published after the run =GEN= over one of its installations, so that each of them holds the tree =GEN= published again.
With one such run, that is the rollback of the run.
With more, it checks everything first, and then makes one pass:

1. Each run to roll back is marked =rolling_back=, with =rollback_to= set to =GEN=.
2. For each installation, the runs over it are taken oldest first, and the tree to put back moves along their hidden names, one exchange for each run, the last one at the stable path.
   The stable path changes once, from the newest tree straight to the tree of =GEN=, and the tree of each run ends at its own hidden name, where the rollback of that run alone would have left it.
   The exchange is the one publication uses, or the three renames when the newest run recorded that the filesystem cannot exchange.
3. The module file goes back to the one the oldest run saved, or is removed when that run made it.
4. Newest first, the links each run made are removed, and the run is marked =rolled_back=, with the message =rolled back to GEN=.

A pass that stops part way is finished by the same command: the =.eb-staged-rebuild-complete= in each tree says how far it got.
Until then the runs stay =rolling_back=, =list= shows their trees as =rolling back=, and =resume= or =rollback= of one of them refuses.
A pass refuses runs that record to a ledger, since a =correction= names a single publication; those are rolled back one at a time.

** What was considered and turned down

- /Replacing the module files first./
  For a moment the new module file would load the old tree.
- /One module at a time, exchange and then module file./
  A failure in the second module would leave the first one published and the second one not, for a build that installs both.
- /=chmod= on the live module file./
  On NFSv4 it rewrites the access-control list; the new file is written with the old file's metadata instead.
- /Rolling back several runs one after the other, newest first./
  The stable path would hold each tree in between, if only for a moment, and a failure half way would leave a tree live that the operator did not ask for.

** Limits

- Other programs do not take the state root's lock: one that reads the module files while a run publishes several of them can see some new and some old.
- Without =RENAME_EXCHANGE=, the stable path is missing for the time between two renames.
- The copy of access-control lists has been tested on ext4 only.
- =rollback --to= needs the hidden tree of every run it rolls back: once =gc= has removed one of them, it refuses.
